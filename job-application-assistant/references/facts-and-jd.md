# 资料、事实与岗位分析

本参考用于所有求职任务。只补充当前智能体运行框架原生能力无法保证的工作流约束，不替代其文件、图像识别、权限或上下文能力。

## 1. 确定模式与路径

1. 查找用户当次指定的配置；存在配置时读取 `assets/config.example.md` 中登记的配置项。
2. 用户当次提供的路径覆盖配置中的同项路径，仅对本次任务生效；不得回写配置。
3. 没有配置或个人档案时进入纯粘贴临时模式：只使用用户当次提供的文本、图片和附件，不自动扫描目录，不创建档案，不写入知识库，不承诺跨会话复用。
4. 用户要求本地归档、长期复用或读取项目文件时，先展示拟创建的配置、档案和写入位置，获得确认后再初始化。复制 `assets/config.example.md` 与 `assets/profile.example.md`，不要修改技能内的模板。
5. 正常模式缺少个人档案路径、微调任务缺少 TeX 模板或原简历 PDF、长期复用缺少事实暂存位置时，指出缺失项并追问。

## 2. 最小化读取与授权

- 每次只处理一个岗位描述（Job Description，JD）；同一岗位的多个招聘沟通与初筛问题可批量处理。
- 只读取完成当前任务必需的授权文件。项目仓库和知识库默认只读，原始模板与原简历 PDF 只读。
- 密钥、凭据、令牌、账号文件、环境秘密文件和任务无关隐私文件始终排除，不复制到正文、归档、日志或外部工具输入。
- 文件无法读取或图片无法辨认时，说明具体文件或区域并请求可读版本；不得把读取失败解释为没有经历、没有技能或没有数据。
- 不主动访问招聘平台，不自动发送、回复、投递或修改招聘平台资料。
- 不通过运行项目、测试、性能基准或安装依赖来制造新的简历数据。

## 3. 建立当次事实视图

把将用于正文的内容逐项归为以下四类；无需默认向用户展示完整清单：

| 类别 | 判定 | 使用规则 |
|---|---|---|
| 已确认事实 | 用户当次明确陈述，或此前已确认且仍可读取的事实条目 | 可使用；用户最新明确修改优先 |
| 证据支持事实 | 可由授权代码、配置、文档、日志、报告或截图直接支持 | 按证据原意使用，不扩大结论 |
| 冲突事实 | 不同来源对同一事项给出不一致内容 | 按来源规则处理；无法解决时追问或列入高风险 |
| 缺失事实 | 任务必需但当前无可靠来源 | 关键事实先追问；非关键表达偏好采用简洁正式风格 |

### 来源优先级

- 基础身份、教育、可承诺条件：以用户明确确认的个人档案为准。
- 项目实现和技术栈：以代码、配置和项目文档等可验证资料为准。
- 项目指标和性能数据：以既有实测证据为准；证据不完整时进入历史确认流程。
- 求职偏好和表达偏好：以用户最新明确确认为准。
- 不得选择对岗位更有利但权威性更低的版本。

### 关键事实

身份、教育、项目经历、个人贡献、实测数据、实习时长、每周天数、到岗时间、工作地点及其他影响真实性或用户权益的信息均为关键事实。缺失时暂停正式正文定稿，用简洁自然语言逐项询问用户；不要输出代码、字段模板、示例答案或占位正文，也不要用常见情况补齐。

## 4. 高风险确认

### 项目数值

1. 优先采用能关联测试代码、环境、步骤和时间的既有日志或报告。
2. 证据不完整时，只有用户明确确认数值确为历史实测结果，并确认测试背景，才可使用。
3. 无证据且未确认的数值删除；不得根据代码复杂度、同类项目或岗位期待估算。
4. 已确认的历史数据形成待归档事实条目；未写入授权暂存位置前，不承诺以后可复用。

### 项目外技术

岗位明确要求但项目未实际使用的技术，只有在用户确认本人具备相应认知或使用经验后，才可加入专业技能板块：

- 只写技术名称，不添加“熟悉”“掌握”“了解”等等级。
- 不写入未使用该技术的项目经历，不虚构场景、成果或贡献。
- 用户未确认时，把它列为差距或待确认项，不写成用户优势。

### 团队项目贡献

先依据资料提出个人贡献边界，再由用户确认。未确认前只能列出有证据的团队成果和“个人贡献待确认”，不得使用“参与”“负责”“主导”“独立完成”等任何措辞替用户划定贡献，也不得把该项目写入正式正文；确认后严格区分团队成果与个人贡献。

### 其他易遗漏的虚构

不得自行添加熟练度、兴趣、态度、出勤或到岗承诺、附件状态、材料提供能力、获奖、证书、排名或求职决定。只有输入资料或用户明确陈述支持时才能写入。尤其不得写“简历已附上”“简历可随时提供”“很感兴趣”“熟悉某技术”，除非事实视图明确支持。

## 5. 分析岗位描述

从用户粘贴文本、图片或附件中提取：

1. 核心职责与硬性要求。
2. 优先条件与核心关键词。
3. 已有且可核验的匹配优势。
4. 关键缺口，尤其是缺乏项目支撑的技术。
5. 本次内容策略：突出、弱化、追问或省略什么。

默认只向用户展示简要匹配与差距，不生成冗长逐项矩阵。岗位描述不完整但不影响核心判断时可先分析；影响岗位或硬性条件判断时先追问。

## 6. 多项目初筛与确认

存在多个候选项目时，不直接生成正式交付物：

1. 分别检查岗位相关性、证据完整度、个人贡献明确程度和内容时效性。
2. 推荐项目及排序，简要说明每个项目的匹配点、证据状态和主要差距；不制造伪精确分数。
3. 请用户确认项目清单和顺序。
4. 确认后才将所选项目用于正式招呼语、招聘沟通回答或简历；确认前只能展示推荐理由和差距。若所选项目的个人贡献、数据或技能仍未确认，继续追问对应边界，不得把“已选项目”当作这些事实也已确认。

用户明确限定只使用某个项目时，视为已确认项目范围，不重复追问；贡献、数据或技能仍有缺口时按高风险规则处理。
